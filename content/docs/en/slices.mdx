# Slices

<Callout variant="info">
One rule governs slicing: 30 minutes of silence. No capacity limits, no topic-shift detection, no ML-driven false splits. Every conversation burst becomes a directory on your timeline — with the conversation, the agent's thinking, and its self-model snapshot all preserved.
</Callout>

Every conversation is captured as a **slice** — a timestamped directory containing everything from that moment. What was said. What the agent was thinking. What it understood about you at the time.

## What a Slice Is

A slice is the storage unit of episodic memory: one conversation burst, one directory on disk. Each slice holds a contiguous sequence of turns — the messages you and the agent exchanged in one sitting — plus parallel records of the agent's internal state.

In v0.4, a slice was a single `.md` file. In v0.5, it is a directory with a richer structure:

```
memory/episodic/slices/2026/07/27/1430/
  timeline/
    core.md       ← the conversation (what was said)
    agent.md      ← the cognition (what the agent was thinking)
  previously.md   ← the agent's self-model snapshot at this moment
```

The path encodes the full timestamp: year/month/day/hour-minute (UTC). A calendar day is a directory that may hold multiple slice directories.

## Dual Timeline: What Happened + What It Thought

The most important structural change in v0.5 is that every slice now carries **two parallel records**.

**`core.md`** is the conversation. Turns formatted as `## Turn N — ISO_TIMESTAMP (role)` headers with the message body below. This is the transcript — what was said, by whom, in what order.

**`agent.md`** is the cognition. It records what the agent was thinking during that conversation: which tools it called, what reasoning it went through, what it decided. The format has two sections:

```
### Thinking
The agent's reasoning for each turn...

### Tools
- readSlice: memory/episodic/slices/2026/07/25/0915 (ok)
- recall: 3 hits found
```

This dual record serves two purposes. First, it powers the **Thoughts** link you see next to every agent message in the historical view — click it, and you see the agent's internal monologue from that exact turn. Second, it gives the evolution system raw material to work with. The evolution agent reads `agent.md` to understand what the agent observed and decided, then uses that to update its self-model.

### Mechanical Cognition Extraction

In v0.4, the agent had to "remember" to call a tool to record its own thinking — which meant it sometimes forgot. In v0.5, cognition extraction is **mechanical**. After every turn, the system automatically extracts the agent's reasoning and tool-call results from the workflow step structure and writes them to `agent.md`. The agent doesn't need to do anything. The system handles it.

This is a small technical detail with a big philosophical implication: the agent's thinking is preserved losslessly, automatically, without relying on the agent to self-report. You get an honest record, not a curated one.

## previously.md Snapshot

Alongside the dual timeline, each slice directory stores a copy of the agent's self-model — `previously.md` — as it existed at the moment that slice closed.

This means you can trace how the agent's understanding of you evolved over time. After your third conversation, what did it believe about your identity? After your thirtieth, how had that changed? Each slice captures a freeze-frame of the agent's mental model, making the evolution visible and auditable.

## YAML Frontmatter

Every `core.md` file opens with `---` delimited YAML metadata, maintained by the system as the conversation progresses:

| Field | Type | Description |
|-------|------|-------------|
| `slice_id` | string | `YYYY-MM-DD-HHMM`, UTC datetime of first message |
| `focus` | string | Core topic, one sentence |
| `status` | `"active"` or `"closed"` | Lifecycle phase |
| `start` | string | UTC ISO 8601 timestamp of first turn |
| `end` | string | UTC ISO 8601 timestamp of last turn (absent while active) |
| `timezone` | string | User's IANA timezone, e.g. `"Asia/Shanghai"` |
| `summary` | string | System-generated recap, one paragraph |
| `open_loops` | string[] | Unresolved questions or threads carried forward |
| `decisions` | string[] | Conclusions or action items from this slice |
| `tags` | string[] | Semantic keywords — these weave into the strand index |
| `related_slices` | string[] | Relative paths of related slices |
| `emotional_tone` | string | `"positive"`, `"neutral"`, `"negative"`, or `"mixed"` |

## Lifecycle

A slice has three states: **open**, **active**, and **closed**.

| Phase | What happens |
|-------|-------------|
| **Open** | You send a message and no slice is active. The system creates a new slice directory, derives the `slice_id` from the current UTC time, and seeds the first user turn. Nothing is written to disk yet — the slice lives in memory. |
| **Extend** | Each subsequent message appends a turn. The slice stays in memory across the session. Periodically a checkpoint snapshot writes the current state to disk. |
| **Close** | After 30 minutes of silence, the slicer triggers. The slice is marked `status: "closed"`, the `end` timestamp is set, `core.md` is finalized, `agent.md` is written with the accumulated cognition, `previously.md` is snapshotted, and the global timeline index is updated. The next message opens a fresh slice. |

> **One rule, no exceptions.** The sole slicing trigger is time silence — 30 minutes (`TIME_SILENCE_THRESHOLD_MS = 1,800,000 ms`) since the last turn. No capacity checks, no topic-shift heuristics. Time-only slicing keeps the system predictable.

On page refresh, the system scans today's directory, finds the most recent slice still marked `active`, and re-hydrates it — you pick up where you left off.

## What Happens When a Slice Closes

Closing a slice isn't just marking a status field. It triggers a cascade:

1. **Finalize core.md** — write the complete conversation transcript with final frontmatter
2. **Write agent.md** — extract and format all cognition from the workflow steps
3. **Snapshot previously.md** — capture the agent's self-model at this moment
4. **Update global timeline** — add this slice to `memory/episodic/timeline.md`
5. **Update strand index** — weave the slice's tags into `memory/episodic/strands.json`
6. **Trigger evolution** — if the conversation produced meaningful observations, fire the evolution workflow to update the agent's self-model

The evolution workflow runs **in parallel** with the chat. It does not block the response. If it fails, the conversation continues normally — the two systems are coupled only through the `previously.md` file on disk.

## A Real Slice Directory

Here is what a completed slice looks like on disk:

```
memory/episodic/slices/2023/04/21/0610/
  timeline/
    core.md       ← 4 turns, ~300 lines
    agent.md      ← 2 thinking blocks, 5 tool calls
  previously.md   ← self-model snapshot: 12 beliefs, 3 long-term categories
```

`core.md`:
```markdown
---
slice_id: 2023-04-21-0610
focus: Housing project delays and trust crisis management
status: closed
start: "2023-04-21T06:10:00.000Z"
end: "2023-04-21T07:18:00.000Z"
timezone: America/Chicago
summary: Contractor qualification and property deed mismatches stalled
  multiple household files, triggering a community trust crisis...
decisions:
  - Prioritize direct phone calls to affected households before public meetings
  - Use 'real blocker plus specific next step' frame in public communication
open_loops:
  - Whether overall community trust can recover after timeline delays
tags:
  - work-pressure
  - housing-project
  - trust-crisis
emotional_tone: mixed
---

## Turn 1 — 2023-04-21T06:10:00.000Z (user)

The housing rehab files that were supposed to close this month are
stalled again...

## Turn 2 — 2023-04-21T06:13:00.000Z (agent)

That sounds rough. What specifically broke down — contractor
qualification, property deeds, or something else?
```

Every part of this file is human-readable, git-diffable, and parseable by any tool that handles Markdown and YAML.

## Design Rationale

- **Time-only slicing** keeps the system predictable. Capacity thresholds and topic-shift heuristics were prototyped and removed in earlier iterations — they added complexity without proven benefit.
- **Dual timeline** (`core.md` + `agent.md`) makes the agent's thinking auditable, searchable, and reviewable. It powers the "Thoughts" link in the historical view and gives the evolution system the raw material it needs.
- **Mechanical cognition extraction** eliminates the reliability problem of asking a model to self-report. The system captures thinking automatically, directly from the workflow step data.
- **previously.md snapshot** per slice makes the agent's evolution visible over time. Each slice is a freeze-frame of the self-model at that moment.
- **Independent evolution workflow** decouples self-model updates from chat responses. Evolution runs in parallel, never blocks the user, and fails gracefully without affecting the conversation.

## Storage Backend

The subsystem transparently switches between two backends:

| Environment | Backend | Selection |
|-------------|---------|-----------|
| Development | Local filesystem | `GITHUB_TOKEN` not set |
| Production | GitHub REST API | `GITHUB_TOKEN` present |

All I/O goes through the same wrapper functions. The same code path works in both environments — no manual switching.
