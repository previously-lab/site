# The Timeline

The timeline is the center of Previously, and it exists twice: as the **interface** you scroll — a wheel of dated slices beside the conversation — and as the **memory index** the agent navigates — a catalog rebuilt from the slice files that gives the agent a map of your past. Both are projections of the same source of truth: the slices themselves.

## Not a chat list, not a search bar

The timeline is the explicit alternative to the two dominant UI patterns of AI chat products. It is **not** a list of conversation threads you must manually manage, rename, delete, and search; and it is **not** a search bar where you type keywords and hope the right memory surfaces. Both patterns push the burden of curating memory onto you.

Previously rejects that assumption. Instead there is a single timeline — your story as an autobiography, oldest at the top, newest at the bottom, with the live conversation at the "now" end.

<Callout variant="info">
**Key takeaway: you do not manage conversations. You scroll through your life.**
</Callout>

## The interface: a wheel beside the conversation

The chat page is a split view: the **timeline wheel** on the left, the conversation — live or historical — on the right.

The wheel is a vertical, virtualized list of **every slice you have** — oldest at the top, newest at the bottom, ending in a "now" row that returns you to the live chat. Each row shows the slice's date, time, and focus line; the timestamps count up and down odometer-style as you scroll, so moving through the past feels like winding a clock. Selecting a past slice plays a **time-travel transition**: a rolling-digit clock spins from where you are to the target slice's moment under a letter-spaced "PREVIOUSLY ON" eyebrow, before the historical view fades in — the verbatim exchanges, the thinking behind them, and the user-card snapshot frozen into that slice.

## The arrival briefing

When the live chat is empty — a first arrival, or a return after the last slice closed — the right panel shows the **arrival briefing** instead of a blank canvas: a film-title-card "PREVIOUSLY ON" over your name, then a hot-start summary drawn from real memory: the last topic, the open loops carried forward, and one-tap suggestion chips. Every section renders only when it has real data — nothing says "last time we talked about" followed by nothing.

## The index: a projection, never a second truth

The timeline is also a maintained **index** over the slice archive. The design rule is one sentence:

<Callout variant="info">
**Slices are the single source of truth; the timeline is a derived projection.** Every catalog entry is rebuildable from the slice files, so a slice can never become unreachable because "the timeline lost it."
</Callout>

The index exists in several renderings, all under `memory/episodic/`, all regenerable:

- **`timeline/index.json`** — the canonical structured catalog, consumed by the interface and by tools.
- **`timeline.md`** — a Markdown projection of the same catalog, grouped by month and day, newest first. This is the file the recall colleague reads as its map.
- **Monthly `_index.json`** — an array of slim entries inside each month's directory, so the interface can browse titles without reading every file.

Each catalog entry is a **pointer with texture** — id, start and end, turn count, `focus`, `summary`, `tags`, emotional tone, open loops, and a `needs_marking` flag. One line is enough to judge relevance, never enough to answer from:

```
- **2026-08-11-1115** Revisiting the performance dispute at the last job, comparing then and now · 14 turns · mixed [status-recall, career-reflection]
```

## weaveTimeline: engineered reconciliation

The index is maintained by `weaveTimeline` — a deterministic reconciliation pass with **zero model calls**:

1. **Enumerate** the slice directories that actually exist on disk — that is the truth.
2. **Load** the current projection.
3. **Diff** — a slice on disk but missing from the catalog is added from its frontmatter; a catalog entry with no slice on disk (a phantom) is dropped. **The slice always wins.**
4. **Rebuild** — resolve each entry's strand membership against `strands.json`, sort chronologically, write out the projections. Within a turn, these writes join that turn's single commit.

A full reconcile is throttled, so most of the time it is one cached read; the slice-close path forces a reconcile so a just-closed slice appears immediately. Because reconciliation is structural, orphaned slices — created but never indexed, closed across a day boundary — are picked up automatically.

## needs_marking: the dry-slice queue

A slice that closed without a `focus`/`summary` is a **dry** slice — anonymous to recall. The reconcile flags these as `needs_marking` instead of hiding them, and two mechanisms keep the count falling:

- **Deterministic fallback at close** — when the analyzer's close-marking comes back incomplete, the slice closes with a deterministic mark (first-turn topic + tags) rather than empty fields.
- **Opportunistic backfill** — only at slice-close boundaries (never mid-conversation), one backfill batch writes focus/summary for up to 3 dry slices and clears their flags. Best-effort by contract: a backfill failure never takes a turn down.

## What the agent sees

The system prompt carries a **timeline brief**: roughly the ten newest pointer lines, each annotated on your local calendar (weekday, days ago — the agent never does date math), plus the catalog totals. The prompt is explicit: *timeline lines are pointers — if a line looks relevant, read the slice before answering from it.*

```
## Timeline (recent)
- **2026-08-11-1115** (08-11 Tue · 6 days ago) Revisiting the performance dispute… · 14 turns · mixed [status-recall,…]
- **2026-08-10-1839** …
- 152 slices back, all traceable
```

Reads then follow a cost ladder — always the smallest sufficient unit first:

| Tool | Who holds it | Purpose |
|------|--------------|---------|
| `recall(question)` | Main agent | Hands the question to the recall colleague — the primary way to access the past |
| `readSlice` | Main agent | Reserved for verifying what recall reported |
| `readTimelineWindow` / `readGlobalTimeline` | Recall colleague | The time axis: orient by date window |
| `readStrand` / `listStrands` | Recall colleague | The topic axis: trace a theme across slices |
| `readSliceSummary` | Recall colleague | Frontmatter only, for a relevance check |
| `readSlice` (range protocol) | Recall colleague | Targeted deep reads, full reads capped at 5 slices |

The full retrieval discipline lives in [Recall](/docs/recall).

## Three timelines

One naming overlap is worth knowing: each slice *directory* also contains a `timeline/` subfolder — those are two of the **three timelines** the product talks about:

- **`core.md`** — the shared record: what you and the agent actually said.
- **`agent.md`** — its thinking: the cognition log behind each turn.
- **Your life** — the third line, the one only you know; the part that never gets written down.

The global timeline described on this page is the catalog *over* all slices' shared records — the index that makes a hundred slices navigable as one line.
