# Architecture

Previously is **local-first**. The product you install is a small CLI that runs the same kernel on your own machine, keeps your memory as a local git repository, and borrows a brain you already pay for. Self-hosting in the cloud — the kernel running on Vercel Workflow with GitHub as the storage backend — remains as the advanced path; it is the same kernel, pointed at a different backend.

## Two Layers: Client and Kernel

| Layer | What it is | What it does |
|-------|------------|--------------|
| **Client** | The `previously-client` npm CLI | Runs and supervises the kernel locally, owns the memory git ledger, delivers the memory skill to your other agents, transcribes their sessions (scribe) |
| **Kernel** | The `previously-kernel` npm package | The actual product: a prebuilt Next.js standalone server with the chat UI, the agent, the episodic memory system, and the evolution loop |

The supply chain is deliberately boring: the client pins an **exact** kernel version (patch included), installs the prebuilt standalone artifact to `~/.previously/kernel/versions/<version>/`, and flips an atomic `current.json` pointer. Upgrading the kernel means upgrading the client package — there is no in-place kernel upgrade or rollback command. Your machine needs no git, no pnpm, no build step.

### The client CLI

```bash
npm i -g previously-client
previously            # the only command you need to remember
```

A bare `previously` is the front door: uninitialized, it walks a guided wizard (where memory lives → which execution backend → whether to transcribe your existing agent histories → keep-or-rebuild → optional token-spending steps, each estimated first, none run by default); initialized, it shows a status panel — kernel and scribe health, the Web UI address, per-source transcription progress. It never starts services and never opens a browser: that is `previously start` and `previously open`. Day-to-day commands are `start` / `stop` / `status` / `logs` / `open`; the advanced surface (`init`, `kernel`, `install`, `watch`, `scribe`, `ingest`, `bridge-exec`) stays out of the way.

Two client subsystems matter architecturally:

- **Skill delivery.** The old MCP server is retired. Instead the client installs a "Previously" skill group (`SKILL.md` + `memory.md` + `ingest.md` + `setup.md`) into each detected agent CLI — Claude Code, Codex, Kimi Code — giving your other agents a strictly-read-only memory protocol. Writes from outside go through `previously ingest`, the single write gateway, which validates a submitted slice and rejects it wholesale on any contract violation.
- **Scribe.** A watcher (chokidar) transcribes your other agents' session logs — Claude Code, Codex, Kimi Code, Gemini CLI — into kernel-shaped time slices, incrementally, byte-identical idempotent, resuming from cursors across restarts. `previously start` launches it as a detached process alongside the kernel.

### The kernel, local and cloud

Locally the kernel is the standalone server the client spawns. In the cloud it is the same codebase deployed to Vercel, where **every chat turn runs inside a durable Vercel Workflow run** — each LLM call and each tool call an individually durable, auto-retried step — with a GitHub repo as the storage backend. There is no database and no persistent server in either world: state lives entirely in files.

### The brain: BYOK or bridge

The kernel needs a model. Two local options, both configured in `config.json`:

- **BYOK** — your own API key (`brain: { type: "api-key", ... }` / the `byok` section); the recommended path.
- **Bridge** — reuse a subscription you already have: the kernel delegates execution to a locally installed agent CLI (`brain: { type: "bridge", agent: "claude" | "codex" | "kimi" }`), dispatched through `previously bridge-exec` over a strict stdin/stdout protocol. The client never touches API keys in this mode — auth is your existing OAuth subscription.

## Memory Is a Git Ledger

Your memory directory is a **local git repository** (pure-JS isomorphic-git — no git binary required). The kernel commits on the same cadence as the cloud backend: **one chat turn = two commits** (`Turn <id> — housekeeping`, then `Turn <id> — agent response`); scribe and ingest commit per batch; `stop` sweeps anything uncommitted. The filesystem stays the source of truth — a failed commit never blocks a write.

The default location sits next to your documents (`~/Documents/Previously`). Pointing the client at an existing Previously repo — say, one cloned back from GitHub — adopts it with its history intact; pointing it at a non-git, non-empty directory is refused. Cursors, logs, and serialized workflow payloads live outside the repo, so the memory repo is safe to push as a private GitHub remote.

## The Durable Turn Workflow

Inside the kernel, the agent is `src/app/api/chat/turn-workflow.ts` — a durable-workflow controller. Every user message triggers one run:

1. **Housekeeping** — resolve or recover the active time slice, apply the slicing rules, append the incoming turn. The turn analyzer scores the turn's fitness signals here, and at a slice boundary the evolution check runs (see below).
2. **Prompt assembly** — the system prompt is assembled from identity, the user card, and the episodic timeline context. Order is a cache decision: stable blocks first (identity constitution, user card), variable blocks last (turn brief, timeline pointers, strands menu, evolution notices), so the provider's prompt cache reuses the long prefix across turns.
3. **Main agent loop** — the main model runs as a `WorkflowAgent`. Each LLM call and each tool call is its own durable step; transient failures retry. If a step is platform-killed or the model hits the token cap, a bounded continuation rebuilds the messages from completed steps and resumes.
4. **Finalize** — the turn is appended to the slice's `timeline/core.md` (the shared record), the agent's cognition — thinking, tool calls, sub-agent reports — is written to `timeline/agent.md` (its own timeline), and the timeline projection and strands are updated.

Because every step is durable, the run survives dropped connections; the client transport re-attaches to the same run and replays what was missed. Each slice stores two of the product's three timelines: `core.md`, the record you share, and `agent.md`, what the agent was thinking. The third — your life outside the chat — is never stored.

## Sub-Agents as Colleagues

The sub-agents are not the main agent's read/write tools. They are **colleagues** with independent judgment: each receives a task, does the work itself — including its own reading — and reports back. The user is always a third party in their exchanges; evidence anchoring (every situational claim hangs on a verbatim quote or slice pointer) applies to all of them.

| Colleague | Role | Budget |
|-----------|------|--------|
| `recall` | Episodic recall: answers natural-language questions about the past, searching the timeline itself (windows → strands → summaries → ≤5 full slice reads). Reports `answer` + `references[]` + `searched[]` + `confidence`; "we don't remember this" is a valid answer | 20 steps · 240s · temp 0.3 |
| `webSearch` | A researcher: provider-executed search plus its own quota-bounded page reads (≤3 pages), synthesizing a real answer with a confidence-and-controversies assessment | 10 steps · 150s |
| `thinkDeep` | A clean-room thinking pod: tool-free, single-shot, context-isolated reasoning. No longer a default per-turn decomposition — invoked only when the main agent needs an unbiased second opinion | one shot |

The main agent's tool surface narrowed accordingly: `readSliceSummary`, `readTimelineWindow`, `readAgentTimeline`, and `webFetch` moved down into the sub-agents. What the main agent kept is `currentTime`, `readPreviously`, the three colleague entry points, and `readSlice` — retained **only as a verification channel** for recall's answers. A post-recall `readSlice` is instrumented as a verify/rework fitness signal: re-doing a colleague's job is remembered, and it costs the recall bucket.

## The Evolution Loop

Self-evolution is Darwinian, and its state lives in the memory repo, not in code:

```
direction.md ──► fitness scoring ──► two-phase evolution ──► mutations.md
(criteria)      (pressure,           (at a slice boundary)     (append-only
                 deterministic                                archive)
                 aggregation)
```

- **Direction** — `memory/evolution/direction.md` is the selection criteria: what "better for you" means, in four fixed sections (Direction / Anti-goals / Evidence / Log). Abstract, cross-slice, append-only log.
- **Fitness** — the turn analyzer scores each slice per bucket (`card` / `recall` / `search` / `thinkdeep` / `interaction`, −2…+1, non-zero scores must carry user-verbatim evidence). Deterministic code aggregates: a 10-slice net ≤ −3 or a single evidence-anchored −2 triggers that bucket's evolution. Scores decide *whether* to evolve, never *what to change*.
- **Two phases, serial, inside housekeeping** — Phase 1 evaluates the direction (low frequency, high bar; "no change" writes nothing); Phase 2 evolves the card and the triggered buckets' playbooks (`memory/agent-playbooks/{recall,search,thinkdeep}.md`, ≤2,000 chars, injected into sub-agent user prompts).
- **Archive** — every accepted mutation is appended to `memory/evolution/mutations.md` with expected benefit and evidence; archiving a new mutation evaluates the previous one on the same target, marking it `ineffective` if its bucket kept losing points. No rollback, no cooldown, no budget.

One writer holds the pen: the evolution agent is the sole writer of card, direction, playbooks, and archive. Recall, webSearch, and thinkDeep are read-only reporters.

## Storage Layout

```
memory/
  episodic/
    slices/YYYY/MM/DD/HHMM/
      timeline/core.md        -- the shared record (frontmatter + turns)
      timeline/agent.md       -- the agent's cognition log
      previously.md           -- user-card snapshot as of this slice
    timeline/index.json       -- canonical slice catalog (projection)
    timeline.md               -- Markdown projection of the catalog
    strands.json              -- strand → slice paths index
    current-previously.md     -- the living user card
  evolution/
    direction.md              -- the selection criteria (four fixed sections)
    fitness.json              -- bounded fitness events + mechanical signals
    mutations.md              -- append-only mutation archive
  agent-playbooks/
    recall.md / search.md / thinkdeep.md   -- evolved per-colleague briefs
```

Everything under `memory/` is plain Markdown/JSON — portable, diffable, human-editable. Slices are the single source of truth; indexes, the card, and the playbooks are derived products.

## Security Model

Security is enforced in TypeScript at the tool boundary, identically in both deployment worlds.

- **Path whitelist** — agent tools may write only under `memory/`, `tasks/`, `sessions/` (`src/lib/whitelist/`). Paths are normalized first (URI-decoded, backslashes converted, `./` / `../` resolved), then empty, absolute, and drive-letter paths are rejected.
- **`src/` is agent-read-only** — it simply does not appear in the whitelist; the sub-agent contracts and tool schemas live there precisely because they are the non-evolvable surface.
- **Same-origin guard** — mutation endpoints (`/api/chat`, `/api/episodic/flush`) accept same-origin browser requests; anything else needs `x-access-key` when `ACCESS_SECRET` is set (cloud deployments opt in).
- **Scoped credentials** — the cloud backend's `GITHUB_TOKEN` is scoped to a single repository; locally, bridge auth rides your existing agent subscriptions and BYOK keys stay in your local config.
