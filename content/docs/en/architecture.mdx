# Architecture

<Callout variant="info">
The core insight of v0.5: the agent decides. It decides when to search memory (Pull, not Push). It evolves its understanding of you in a parallel workflow (independent, not embedded). It navigates memory concepts (slices, strands, timelines) rather than file paths. Everything runs on your GitHub repo — no database, no vector store.
</Callout>

Previously runs two independent Vercel Workflows in parallel — chat and evolution — coupled only through files on disk. The agent pulls context on demand instead of having it pushed. Tools express memory semantics, not filesystem operations.

## The Three Layers

The system is split into three layers, each with a distinct responsibility and a hard boundary between them:

| Layer | What it is | What it does |
|-------|------------|--------------|
| **Browser** | Next.js App Router UI | Renders the chat surface, horizontal timeline, Phase Indicator, and Previously Bar. Captures input. Streams responses. That is all — no business logic, no state machine, no local memory. |
| **Vercel Orchestration** | Two independent Workflows | **Chat workflow** (`POST /api/chat`): runs the agent loop, streams responses. **Evolution workflow** (`POST /api/evolution`): runs the Previously Agent, updates the self-model. The two run in parallel, coupled only through `previously.md` on disk. |
| **GitHub Private Repo** | The single source of truth | Holds everything: `src/` (agent-read-only), `memory/` (episodic slices, previously.md, timeline index, strand index), `tasks/`, `sessions/`. |

### Execution Model: Vercel Workflow

Every chat turn runs inside a durable Vercel Workflow run. This means:

- **Resumable streaming** — the response streams to the client. If the connection drops, the workflow continues running on Vercel's infrastructure and the client can reconnect.
- **Durable steps** — each LLM call and each tool call is an individually durable, automatically retried workflow step. A transient API failure retries without losing the turn's progress.
- **Parallel workflows** — the chat and evolution workflows are fully independent. Chat does not wait for evolution. Evolution does not block the chat response. If evolution fails, chat continues normally. The two systems are decoupled at the infrastructure level.

There is intentionally no database or KV store. State lives in GitHub files. Workflow provides durability for execution; GitHub provides durability for data.

## The Chat Workflow: Pull-Based Agent Loop

The chat workflow is `src/app/api/chat/turn-workflow.ts`. Each user message triggers these steps:

### 1. Housekeeping

Resolve or create the active time slice. If no slice is active, recover the last-known slice from disk. Apply the 30-minute silence rule: if the user has been inactive that long, close the old slice and open a new one. Append the incoming turn.

### 2. Assemble Baseline Context

The system prompt is built from two things:
- **System directives** — the agent's role, capabilities, and rules (compiled at build time)
- **previously.md** — the agent's current understanding of the user (read from disk at request time)

That's it. No pre-loaded recall results. No pre-assembled timeline context. No mandatory Flash call. The agent starts with its understanding of who you are, and pulls everything else on demand.

### 3. Agent Loop (Pro Model)

The main model (DeepSeek V4 Pro, with optional thinking mode) enters a tool-use loop:

```
Pro receives message + previously.md
  → Pro decides: respond directly, or search memory?
    → If search: call recall tool
      → Flash sub-agent scans timeline, returns pointers
      → Pro reads relevant slices via readSlice
    → Pro responds
  → (optional) Pro calls additional tools (readStrand, readTimeline, etc.)
  → Loop continues until Pro finishes (max 20 steps)
```

The key difference from v0.4: the system does not pre-decide what context the agent needs. The agent decides.

### 4. Cognition Extraction

After each turn, the system mechanically extracts the agent's reasoning and tool-call results from the workflow step data and writes them to `agent.md`. This is automatic — the agent doesn't need to call a tool to record its thinking. The extraction reads `result.steps[].reasoning` for the thinking text and matches tool results by `toolCallId`. No model involvement, no missed recordings.

### 5. Slice Snapshot

On turn completion, the slice state is snapshotted to disk. The global timeline index is updated. The strand index is refreshed with any new tags. If the slice is closing (30-minute silence rule), the evolution workflow is triggered.

## The Evolution Workflow: Independent Self-Model Updates

The evolution workflow is `src/app/api/evolution/route.ts`. It runs as a **fully independent Vercel Workflow**, in parallel with chat:

```
Client                          Server
  │                               │
  ├─ POST /api/chat ──────────────┼── chat workflow (Pro agent loop)
  │                               │
  ├─ POST /api/evolution ─────────┼── evolution workflow (Previously Agent)
  │  (parallel, don't wait)       │      │
  │                               │      ├─ readEvolutionContext
  │                               │      │   ├─ Read current slice (core.md + agent.md)
  │                               │      │   ├─ Read previously.md
  │                               │      │   └─ Extract recent turns
  │                               │      │
  │                               │      └─ finalizeEvolution
  │                               │          ├─ Run Previously Agent (Pro, no thinking)
  │                               │          ├─ Apply mutations via previously-updater
  │                               │          ├─ Write updated previously.md
  │                               │          └─ Stream results via SSE
  │                               │
  │  ←── data-evolution chunks ───┼── Previously Bar updates in real time
```

### Why It's Independent

1. **Decoupling** — Chat and evolution know nothing about each other. They share only `previously.md` on disk. This is a clean microservice-style boundary.
2. **Parallelism** — Evolution never delays a chat response. Both run at the same time.
3. **Fault isolation** — If evolution fails, chat doesn't care. The Previously Bar shows a red error state, but the conversation continues.
4. **Independent retry** — Evolution has its own durable steps and retry logic. A transient failure in the Previously Agent call doesn't affect anything else.

### The Previously Agent

The evolution workflow runs a Pro model (DeepSeek V4 Pro, **without** thinking mode — this is structured review, not creative work). It makes a three-gate decision:

1. **Nothing to do** → return empty mutations, immediately end
2. **Shallow edit** → from pre-loaded data (previously.md + current conversation + recent turns), decide what changed
3. **Deep exploration** → call `readSlice`, `readAgentTimeline`, or `readPreviously` tools to investigate before deciding

The Previously Agent's mutations are applied through `previously-updater.ts` — a **pure function** with no I/O and no LLM calls. It takes the current previously.md and a list of mutation operations (observe, reinforce, contradict, discard, expire, promote, demote), and returns the updated document. This separation — model decides, pure function applies — keeps the system testable and predictable.

## Capabilities Module: Single Source of Truth

`src/lib/capabilities.ts` is the one place that determines what the app can do. Every other module queries it instead of reading environment variables directly:

```
DEEPSEEK_API_KEY exists?
├─ NO  → App unavailable
└─ YES → GITHUB_TOKEN exists?
          ├─ NO  → Demo mode: can chat, cannot write, cannot loop
          └─ YES → Production mode: full functionality
```

This replaces the v0.4 pattern where 8+ files each read `process.env` independently. The capabilities module is for engineering code only — the AI model layer never imports it. The model learns its limitations through tool executor return values, not through injected system prompt flags.

## Conceptual Memory Tools

The agent's tools express **memory semantics**, not filesystem operations. This is a deliberate design choice: the agent should navigate memory the way a person thinks about it, not the way a filesystem organizes it.

| Tool | Semantic concept | What it actually does |
|------|-----------------|---------------------|
| `recall` | Search the past | Launch a Flash sub-agent to scan the global timeline + strand index, return pointers to relevant slices |
| `readSlice` | Open a memory | Construct the path to a slice directory, read both core.md and agent.md, return structured content |
| `readTimeline` | Browse the timeline | Read the global timeline index (`timeline.md`), return all available slices with summaries |
| `readStrand` | Trace a topic | Read the strand index, follow a keyword to its slice paths, read those slices |
| `listStrands` | Browse all topics | Read the strand index, return all keyword entries |
| `readAgentTimeline` | Review past thinking | Read agent.md files across slices to trace the agent's cognitive history |
| `readPreviously` | Check past impressions | Read historical previously.md snapshots from earlier slices |

Each tool constructs paths internally. The agent never sees or constructs a file path. The path whitelist (`memory/`, `tasks/`, `sessions/`) is enforced at the tool executor level — the agent can only access what the tools allow, and the tools can only access whitelisted directories.

## The Dual Timeline

Every slice stores two parallel records:

```
memory/episodic/slices/YYYY/MM/DD/HHMM/
  timeline/
    core.md       ← the conversation (what was said)
    agent.md      ← the cognition (what the agent was thinking)
  previously.md   ← the self-model snapshot
```

`core.md` is the transcript. `agent.md` is the internal record — reasoning text and tool-call results, mechanically extracted from workflow step data. Together they power the historical view (conversation + "Thoughts" link) and give the evolution system the raw material it needs.

## Shared Infrastructure

### Turn Parser (`turn-parser.ts`)

A shared utility for parsing slice IDs and conversation turns:
- `parseSliceId()`: converts `YYYY-MM-DD-HHMM` to path segments
- `parseTurns()`: parses `## Turn N -- ISO_TIMESTAMP (role)` headers from core.md

Used by both tool executors and evolution steps — avoids duplicated parsing logic.

### Slice Cache (`slice-cache.ts`)

A client-side in-memory cache (`Map<sliceId, {content, timestamp}>`) with a 5-minute TTL. When the user clicks back to a recently viewed slice, the content returns instantly from cache — no API call, no loading state. Auto-expires stale entries.

### Global Timeline Index (`timeline.md`)

A single flat file containing summaries of all closed slices. The recall system reads this as its starting point — one read, everything visible. Regenerated incrementally when slices close. Stale-detected (6-hour threshold) and auto-regenerated if needed.

## Frontend Architecture

The page uses a two-screen CSS document flow — no JavaScript height hacks, no virtual scroller:

- **Hero** — `h-screen`, full viewport. "Previously on {name}" with text-reveal animation.
- **Timeline** — `sticky top-12`, snaps below the fixed header and stays visible.
- **Content area** — `min-h-screen`, natural document flow containing either live chat or historical view.
- **Chat input** — `fixed bottom-0` with translucent backdrop (`bg-background/90 backdrop-blur-md`).
- **Previously Bar** — `fixed bottom-12`, always visible between content and input.

The message area streams through React Server Components with Suspense boundaries, enabling the page shell to render immediately while data streams in.

## Security Model

Security is enforced entirely in TypeScript at the tool boundary:

### Path Whitelist

Only three directories are writable: `memory/`, `tasks/`, `sessions/`. `normalizePath()` decodes URI components, converts backslashes, resolves `./` and `../`, strips leading slashes. Then `isPathAllowed()` rejects empty paths, absolute Unix paths, and drive-letter paths before matching against allowed prefixes.

### Protected System Paths

Within the whitelist, certain paths are readable but **not writable** by the generic tools: `memory/episodic/` (system-owned slices and indexes), any `_index.json` file, `strands.json`, and `timeline.md`. These are only modified through their dedicated system functions.

### `src/` Is Agent-Read-Only

The `src/` directory does not appear in the whitelist. No agent tool can write there. The agent can read `src/` through git, but cannot modify it.

### Data Source Auto-Detection

The capabilities module centralizes data-source resolution. When `GITHUB_TOKEN` is set, the system uses the GitHub API against the user's private repo. Without a token, demo mode activates — serving benchmark data from a public repo. Writes are accepted but discarded in demo mode. A demo badge in the header indicates the current mode.

## What Was Removed (v0.4 → v0.5)

The v0.5 architecture is simpler despite being more capable. Key removals:

| Removed | Why | Replaced by |
|---------|-----|------------|
| `profile.md` + profile writer | Separate identity file, manually patched | previously.md User identity section |
| `memory/nodes/` extractor | Agent-authored knowledge cards | previously.md beliefs with evidence trails |
| `updateUserProfile` tool | Model-called profile patching | Evolution workflow (autonomous, independent) |
| File-driven loop engine | Manual checkpoint serialization | Vercel Workflow native durability |
| Unified Flash call (per-turn) | Mandatory context pre-loading | On-demand `recall` tool |
| Archive sync | Session/task archival | Superseded by workflow + slice systems |
| Vertical timeline panel (~580 lines) | Sidebar with date-grouped cards | Horizontal timeline (115 lines) |
| Filesystem-concept tools | `readFile`, `writeFile`, etc. | Conceptual memory tools (7 tools) |
