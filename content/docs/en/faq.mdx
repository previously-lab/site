# FAQ

<Callout variant="info">
Your memory is a directory tree of Markdown files in a git repo — slices, a self-model, a timeline index, and a strand index. That is it. No database, no vector store, no proprietary format.
</Callout>

Common questions about how Previously works, what it costs, and where the boundaries are.

## Is there a database?

No. All state is plain Markdown files with YAML frontmatter, stored in a GitHub repository. The data model consists of:

- **Slices** — directories at `memory/episodic/slices/YYYY/MM/DD/HHMM/` containing `core.md` (conversation) and `agent.md` (cognition)
- **previously.md** — the agent's self-model, a structured Markdown file at `memory/episodic/previously.md`
- **timeline.md** — a flat global index of all closed slices
- **strands.json** — a keyword-to-slice-paths map
- **Tasks and sessions** — Markdown files in `tasks/` and `sessions/`

No Postgres, no SQLite, no Pinecone. Files are the database.

## Can other tools read my memory?

Yes. Memory is plain Markdown with YAML frontmatter — no SDK, no API gateway, no vendor lock-in. Previously writes memories. Claude Code reads them. Any editor opens them. Any tool that can parse Markdown and read a git repo can read your memory.

This portability is a core design goal. You never need to export or migrate data; you just point a different tool at the same repo.

## Does it forget in a long conversation?

No — not the way a growing prompt window does. Previously has no chat threads that accumulate indefinitely. The system prompt contains `previously.md` (compact, bounded — at most 53 beliefs across all categories). Everything else is pulled on demand: the agent calls `recall` when it needs to search the past, `readSlice` when it needs to read a specific conversation. Each request stays bounded and relevant.

There is no point where the agent suddenly forgets the beginning of a long exchange, because there is no single long exchange — context is rebuilt every round from the agent's self-model plus targeted retrievals.

## How is a slice closed?

One rule: 30 minutes of silence since the last message. The threshold is hardcoded at `TIME_SILENCE_THRESHOLD_MS = 30 * 60 * 1000`. No capacity limits, no topic-shift detection. When a slice closes, the system: finalizes `core.md`, writes `agent.md` with mechanically extracted cognition, snapshots `previously.md`, updates the global timeline index, refreshes the strand index, and triggers the evolution workflow.

## What's the difference between previously.md and a user profile?

A user profile is something you fill out. previously.md is something the agent writes and maintains itself.

After every conversation, a dedicated evolution workflow runs a separate model that reviews what the agent observed and decides whether its understanding of you needs to change. It can observe new things, reinforce existing impressions, correct wrong ones, and expire outdated context. The file carries evidence trails — every belief links back to the specific conversations that support it.

You can read it at any time by clicking the Previously Bar. You can correct it by telling the agent "no, that's not right." But you never write to it directly. It is the agent's understanding of you, maintained by the agent, for the agent.

## What does the agent see about me?

When you send a message, the agent's system prompt includes `previously.md` in full — its complete understanding of you: your identity, patterns, how to best help you, and your current context. That's the baseline. Everything else is pulled on demand: the agent calls `recall` to search your past conversations, `readSlice` to read specific ones, and other memory tools as needed.

The agent maintains what it knows within strict capacity limits (identity ≤ 20 beliefs, patterns ≤ 8, strategies ≤ 15, context ≤ 10). When a category is full, the lowest-confidence, least-recent belief is evicted. The agent must decide what matters enough to keep.

## Is it production-ready?

No. Previously is experimental v0.5. It is a one-person research project in active early development — not yet ready for personal or production use. Expect rough edges, breaking changes, and features still on the roadmap. The author commits to long-term maintenance.

## Do code and memory share a repo?

They can. They can also be separate. The environment variables `GITHUB_REPO_OWNER` and `GITHUB_REPO_NAME` can point at a dedicated private memory repo distinct from the code repo. The project's own convention co-locates them, but the configuration gives you the choice.

## How much does it cost to run?

Two cost centers:

- **LLM API usage** — Previously runs on your own DeepSeek API key. The two-tier architecture (Flash for fast recall searches, Pro for reasoning and responses) is cost-motivated: cheap passes handle the common case, expensive reasoning runs only when needed. In v0.5's Pull architecture, Flash doesn't run at all for conversations that don't need memory retrieval.
- **Hosting** — Vercel (free tier may cover light usage; sustained use will likely need a paid plan). GitHub repo storage is effectively free.

Previously charges no subscription, no per-seat fee, and no usage markup. You supply the infrastructure and the keys; the project is the orchestration layer.

## Is my data private?

Yes, by design. Memory lives in a GitHub repository you own (the deployment guide recommends a private repo). Access is controlled by a fine-grained personal access token scoped to contents read/write on a single repository. There is no platform database that holds your conversations. No third-party server stores your slices, your previously.md, or your strand index.

You own the data outright. Clone it, back it up, move it to another provider — it's just files in a git repo.

## What happened to memory nodes and profile.md?

They were consolidated into previously.md in v0.5. The old system had three separate things: a `profile.md` identity file, `memory/nodes/` knowledge cards, and a `updateUserProfile` tool. The new system has one thing: previously.md, maintained by one process (the evolution workflow), visible in one place (the Previously Bar). Every belief carries an evidence trail back to specific conversations.

## Can the agent run tasks while I'm away?

Yes — background loops were re-enabled in v0.5. The agent can start persistent background tasks via the `startLoop` tool. Loops use the same Vercel Workflow infrastructure as chat turns (durable execution, automatic retry). In demo mode, the tool returns a message guiding you to deploy your own instance — loops require a GitHub-connected setup.
