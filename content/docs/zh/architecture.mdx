# 架构

<Callout variant="info">
v0.5 的核心洞察：agent 自行决定。它决定何时搜索记忆（Pull，而非 Push）。它在并行工作流中演化对你的理解（独立，而非嵌入）。它导航的是记忆概念（slices、strands、时间线）而非文件路径。一切运行在你的 GitHub 仓库上——没有数据库，没有向量存储。
</Callout>

Previously 运行两个独立的 Vercel Workflow——聊天和演化——仅通过磁盘上的文件耦合。agent 按需拉取上下文而非被动接收。工具表达的是记忆语义，而非文件系统操作。

## 三层架构

系统分为三个层，每层有明确的职责和严格的边界：

| 层 | 是什么 | 做什么 |
|-------|------------|--------------|
| **浏览器** | Next.js App Router UI | 渲染聊天界面、水平时间线、Phase Indicator 和 Previously Bar。捕获输入。流式输出响应。仅此而已——没有业务逻辑，没有状态机，没有本地记忆。 |
| **Vercel 编排层** | 两个独立 Workflow | **聊天工作流**（`POST /api/chat`）：运行 agent 循环，流式输出响应。**演化工作流**（`POST /api/evolution`）：运行 Previously Agent，更新自我模型。两者并行运行，仅通过磁盘上的 `previously.md` 耦合。 |
| **GitHub 私有仓库** | 单一事实来源 | 保存一切：`src/`（agent 只读）、`memory/`（情景 slices、previously.md、时间线索引、strand 索引）、`tasks/`、`sessions/`。 |

### 执行模型：Vercel Workflow

每个聊天轮次在一个持久化的 Vercel Workflow 运行中执行。这意味着：

- **可恢复的流式响应**——响应流式传输到客户端。如果连接断开，workflow 继续在 Vercel 基础设施上运行，客户端可以重新连接。
- **持久化步骤**——每个 LLM 调用和每个工具调用都是独立持久化、自动重试的 workflow step。瞬时 API 故障会重试，不会丢失轮次进度。
- **并行工作流**——聊天和演化工作流完全独立。聊天不等待演化。演化不阻塞聊天响应。如果演化失败，聊天正常继续。两个系统在基础设施层面解耦。

系统有意不引入数据库或 KV 存储。状态完全存在于 GitHub 文件中。Workflow 为执行提供持久性，GitHub 为数据提供持久性。

## 聊天工作流：基于 Pull 的 Agent 循环

聊天工作流位于 `src/app/api/chat/turn-workflow.ts`。每条用户消息触发以下步骤：

### 1. 日常维护

解析或创建当前的时间 slice。如果没有活跃 slice，从磁盘恢复最近已知的 slice。应用 30 分钟静默规则：如果用户已静默超过该时长，关闭旧 slice 并打开新 slice。追加当前轮次。

### 2. 组装基线上下文

系统提示词由两部分构建：
- **系统指令**——agent 的角色、能力和规则（构建时编译）
- **previously.md**——agent 对用户的当前理解（请求时从磁盘读取）

仅此而已。没有预加载的 recall 结果。没有预组装的时间线上下文。没有强制性的 Flash 调用。agent 以它对你身份的理解开始，按需拉取其余一切。

### 3. Agent 循环（Pro 模型）

主模型（DeepSeek V4 Pro，可选推理模式）进入工具使用循环：

```
Pro 收到消息 + previously.md
  → Pro 决定：直接回复，还是搜索记忆？
    → 如果搜索：调用 recall 工具
      → Flash 子 agent 扫描时间线，返回指针
      → Pro 通过 readSlice 读取相关 slice
    → Pro 回复
  → （可选）Pro 调用其他工具（readStrand、readTimeline 等）
  → 循环继续直到 Pro 完成（最多 20 步）
```

与 v0.4 的关键区别：系统不预先决定 agent 需要什么上下文。agent 自行决定。

### 4. 认知提取

每个轮次后，系统从 workflow step 数据中机械提取 agent 的推理和工具调用结果，写入 `agent.md`。这是自动的——agent 无需调用工具来记录其思考。提取过程读取 `result.steps[].reasoning` 获取思考文本，并通过 `toolCallId` 匹配工具结果。无需模型参与，不会遗漏记录。

### 5. Slice 快照

轮次完成后，slice 状态快照到磁盘。全局时间线索引更新。strand 索引用新标签刷新。如果 slice 正在关闭（30 分钟静默规则），演化工作流被触发。

## 演化工作流：独立的自我模型更新

演化工作流位于 `src/app/api/evolution/route.ts`。它作为一个**完全独立的 Vercel Workflow** 运行，与聊天并行：

```
客户端                          服务端
  │                               │
  ├─ POST /api/chat ──────────────┼── 聊天工作流（Pro agent 循环）
  │                               │
  ├─ POST /api/evolution ─────────┼── 演化工作流（Previously Agent）
  │  （并行，不等待）              │      │
  │                               │      ├─ readEvolutionContext
  │                               │      │   ├─ 读取当前 slice（core.md + agent.md）
  │                               │      │   ├─ 读取 previously.md
  │                               │      │   └─ 提取最近轮次
  │                               │      │
  │                               │      └─ finalizeEvolution
  │                               │          ├─ 运行 Previously Agent（Pro，无思考模式）
  │                               │          ├─ 通过 previously-updater 应用变更
  │                               │          ├─ 写入更新后的 previously.md
  │                               │          └─ 通过 SSE 流式输出结果
  │                               │
  │  ←── data-evolution 数据块 ───┼── Previously Bar 实时更新
```

### 为什么独立

1. **解耦**——聊天和演化彼此一无所知。它们仅共享磁盘上的 `previously.md`。这是一个清晰的微服务式边界。
2. **并行性**——演化从不延迟聊天响应。两者同时运行。
3. **故障隔离**——如果演化失败，聊天不关心。Previously Bar 显示红色错误状态，但对话继续。
4. **独立重试**——演化有自己的持久化步骤和重试逻辑。Previously Agent 调用中的瞬时故障不影响任何其他内容。

### Previously Agent

演化工作流运行一个 Pro 模型（DeepSeek V4 Pro，**不带**思考模式——这是结构化审查，而非创造性工作）。它做三阶段决策：

1. **无需操作**→ 返回空变更，立即结束
2. **浅层编辑**→ 从预加载数据（previously.md + 当前对话 + 最近轮次）判断什么变了
3. **深层探索**→ 调用 `readSlice`、`readAgentTimeline` 或 `readPreviously` 工具进行深入调查后再做决定

Previously Agent 的变更通过 `previously-updater.ts` 应用——一个**纯函数**，无 I/O、无 LLM 调用。它接受当前的 previously.md 和一系列变更操作（observe、reinforce、contradict、discard、expire、promote、demote），返回更新后的文档。这种分离——模型决定，纯函数应用——使系统可测试且可预测。

## 能力模块：单一事实来源

`src/lib/capabilities.ts` 是确定应用能做什么的唯一位置。所有其他模块查询它而非直接读取环境变量：

```
DEEPSEEK_API_KEY 存在？
├─ 否  → 应用不可用
└─ 是  → GITHUB_TOKEN 存在？
          ├─ 否  → Demo 模式：可聊天、不可写入、不可循环
          └─ 是  → 生产模式：全功能
```

这取代了 v0.4 中 8+ 个文件各自独立读取 `process.env` 的模式。能力模块仅供工程代码使用——AI 模型层从不导入它。模型通过工具执行器的返回值了解其限制，而非通过注入的系统提示标记。

## 记忆概念工具

agent 的工具表达的是**记忆语义**，而非文件系统操作。这是一个深思熟虑的设计选择：agent 应如人类思考记忆的方式那样导航记忆，而非如文件系统组织数据的方式那样。

| 工具 | 语义概念 | 实际上做什么 |
|------|-----------------|---------------------|
| `recall` | 搜索过去 | 启动 Flash 子 agent 扫描全局时间线 + strand 索引，返回指向相关 slice 的指针 |
| `readSlice` | 打开一段记忆 | 构造 slice 目录路径，读取 core.md 和 agent.md，返回结构化内容 |
| `readTimeline` | 浏览时间线 | 读取全局时间线索引（`timeline.md`），返回所有可用 slice 及其摘要 |
| `readStrand` | 追踪一个主题 | 读取 strand 索引，跟踪关键词到其 slice 路径，读取那些 slice |
| `listStrands` | 浏览所有主题 | 读取 strand 索引，返回所有关键词条目 |
| `readAgentTimeline` | 回顾过去思考 | 读取跨 slice 的 agent.md 文件，追踪 agent 的认知历史 |
| `readPreviously` | 查看过去的印象 | 读取之前 slice 中的历史 previously.md 快照 |

每个工具在内部构造路径。agent 从不看到或构造文件路径。路径白名单（`memory/`、`tasks/`、`sessions/`）在工具执行器层面强制执行——agent 只能访问工具允许的内容，而工具只能访问白名单目录。

## 双时间线

每个 slice 存储两条并行记录：

```
memory/episodic/slices/YYYY/MM/DD/HHMM/
  timeline/
    core.md       ← 对话内容（说了什么）
    agent.md      ← 认知内容（agent 在想什么）
  previously.md   ← 自我模型快照
```

`core.md` 是记录。`agent.md` 是内部记录——从 workflow step 数据中机械提取的推理文本和工具调用结果。两者共同驱动历史视图（对话 + "Thoughts" 链接），并为演化系统提供所需原始素材。

## 共享基础设施

### Turn Parser（`turn-parser.ts`）

用于解析 slice ID 和对话轮次的共享工具：
- `parseSliceId()`：将 `YYYY-MM-DD-HHMM` 转换为路径段
- `parseTurns()`：从 core.md 解析 `## Turn N -- ISO_TIMESTAMP (role)` 标题

被工具执行器和演化步骤共同使用——避免重复的解析逻辑。

### Slice Cache（`slice-cache.ts`）

客户端内存缓存（`Map<sliceId, {content, timestamp}>`），5 分钟 TTL。当用户点击回到最近查看过的 slice 时，内容从缓存即时返回——无 API 调用、无加载状态。过期条目自动清除。

### 全局时间线索引（`timeline.md`）

一个包含所有已关闭 slice 摘要的单一扁平文件。recall 系统以此为起点——一次读取，一览全貌。在 slice 关闭时增量重新生成。过期检测（6 小时阈值），需要时自动重新生成。

## 前端架构

页面采用双屏 CSS 文档流——无 JavaScript 高度技巧，无虚拟滚动器：

- **Hero**——`h-screen`，全视口。"Previously on {名字}" 带文字揭示动画。
- **时间线**——`sticky top-12`，吸附在固定头部下方并保持可见。
- **内容区域**——`min-h-screen`，自然文档流，包含实时聊天或历史视图。
- **聊天输入**——`fixed bottom-0` 带半透明背景（`bg-background/90 backdrop-blur-md`）。
- **Previously Bar**——`fixed bottom-12`，始终可见于内容和输入之间。

消息区域通过 React Server Components 搭配 Suspense 边界进行流式渲染，使页面外壳能够立即渲染，而数据流式加载进来。

## 安全模型

安全完全在 TypeScript 层面、在工具边界处执行：

### 路径白名单

仅三个目录可写入：`memory/`、`tasks/`、`sessions/`。`normalizePath()` 解码 URI 组件、转换反斜杠、解析 `./` 和 `../`、去除前导斜杠。然后 `isPathAllowed()` 拒绝空路径、绝对 Unix 路径和驱动器字母路径，再匹配允许的前缀。

### 受保护的系统路径

在白名单内，某些路径可读取但**不可**由通用工具写入：`memory/episodic/`（系统拥有的 slices 和索引）、任何 `_index.json` 文件、`strands.json` 和 `timeline.md`。这些只能通过其专用系统函数修改。

### `src/` 为 Agent 只读

`src/` 目录不在白名单中。没有 agent 工具可以在那里写入。agent 可以通过 git 读取 `src/`，但不能修改它。

### 数据源自动检测

能力模块集中化数据源解析。当设置 `GITHUB_TOKEN` 时，系统使用 GitHub API 操作用户的私有仓库。无 token 时，demo 模式激活——从公共仓库提供基准测试数据。写入在 demo 模式中被接受但丢弃。头部中的 demo 徽章指示当前模式。

## 移除了什么（v0.4 → v0.5）

v0.5 架构更简单但能力更强。关键移除项：

| 移除 | 原因 | 被取代为 |
|---------|-----|------------|
| `profile.md` + profile writer | 独立的身份文件，手动修补 | previously.md 用户身份部分 |
| `memory/nodes/` extractor | agent 编写的知识卡片 | 带证据链的 previously.md 信念 |
| `updateUserProfile` 工具 | 模型调用的 profile 修补 | 演化工作流（自主、独立） |
| 文件驱动的循环引擎 | 手动检查点序列化 | Vercel Workflow 原生持久性 |
| 统一 Flash 调用（每轮） | 强制上下文预加载 | 按需 `recall` 工具 |
| Archive sync | 会话/任务归档 | 被工作流和 slice 系统取代 |
| 垂直时间线面板（~580 行） | 带按日期分组的卡片侧边栏 | 水平时间线（115 行） |
| 文件系统概念工具 | `readFile`、`writeFile` 等 | 记忆概念工具（7 个工具） |
