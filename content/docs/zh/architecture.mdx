# 架构

Previously 是部署在 Vercel 上的云端 Agent,读取 GitHub 文件、调用 LLM、把响应流式传回——没有数据库,没有定时任务,没有持久化服务器。让它与众不同的,是**每一轮聊天都跑在一次耐久的 Vercel Workflow 运行里**:每一次 LLM 调用、每一次工具调用,都是单独耐久、自动重试的步骤。GitHub 仍是记忆的唯一事实来源——Workflow 只是执行容器。

## 三层架构

系统分为三个层,每层有明确的职责和严格的边界:

| 层 | 是什么 | 做什么 |
|-------|------------|--------------|
| **浏览器 / 手机** | Next.js App Router UI | 渲染聊天界面。捕获输入。流式输出响应。仅此而已——没有业务逻辑,没有状态机,没有本地记忆。 |
| **Vercel** | 编排层 | 接收触发 → 读 GitHub 状态 → 运行 Agent workflow → 写回。无状态、事件驱动、耐久。 |
| **GitHub 私有仓库** | 单一事实来源 | 保存一切:`src/`(agent 只读)、`memory/`、`tasks/`、`sessions/`(agent 可读写)。代码和数据共存于一个仓库中。 |

<Callout variant="info">
**关键要点:没有数据库,没有常驻 agent,没有持久连接。** Previously 完全运行在 Vercel 的请求生命周期内。你发送一条消息,回合 workflow 触发,响应流式传回。响应结束时没有后台进程。(耐久后台循环是设计的一部分,但暂时禁用——即使它们启用,状态也持久化到仓库,而不是某台服务器。)
</Callout>

## 耐久的回合 Workflow

整个 Agent 是 `src/app/api/chat/turn-workflow.ts`——一个 `"use workflow"` 控制器。每个用户消息触发一次这样的运行:

1. **日常维护(housekeeping)** —— 解析或恢复当前 Slice,应用约 15 分钟静默规则(可配置),追加本轮用户消息。
2. **worker 扫描** —— 一个廉价 worker 模型(从主模型供应商派生)在一次调用里扫描近期 Slice 摘要找回忆指针、维护 Slice 元数据,并应用**语义门**:琐碎回合(「谢谢」「继续」)不产生标签、不进 Strand 索引。Slice 关闭时,另有一个 worker 通道整理 Strand 索引(合并语义重复项),时间线投影也同时被校正。
3. **组装 prompt** —— 系统 prompt 由身份、用户卡片、情景时间线上下文组装而成。顺序是一个缓存决策:稳定的块在前(身份宪法、用户卡片),可变的块在后(回合简报、时间线指针、Strand 菜单、演化与演示通知),让供应商的 prompt 缓存跨回合复用这段长前缀。
4. **主模型 Agent 循环** —— 主模型作为 `WorkflowAgent`(`@ai-sdk/workflow`)运行。每一次 LLM 调用、每一次工具调用都是它自己的耐久步骤:工具执行器是 `src/app/api/agent/tool-executors.ts` 里独立的 `"use step"` 函数,运行时对瞬时失败自动重试。Agent 推理、回忆、读取、回答。如果某个步骤被平台杀死或模型撞上 token 上限,回合不会就此死掉——一个有界的续跑机制用已完成步骤重建消息,从断点接着跑。
5. **收尾(finalize)** —— 本轮追加进 Slice 的 `timeline/core.md`(共同的记录),Agent 的认知——思考、工具调用、子 agent 报告——写入 `timeline/agent.md`(它自己的时间线),并更新时间线投影与 Strand。

因为每一步都耐久,运行能扛住断线。客户端的 `WorkflowChatTransport` 在标签页回到前台时重新挂到同一次运行上,回放错过的东西。后台循环用同一个 agent 层,跑在独立的 workflow 运行里(目前禁用——见下文「工具」)。

因此每个 Slice 存着产品三条时间线中的两条:`core.md` 是你们共同的记录,`agent.md` 是它当时的思考。第三条时间线——你在聊天之外的生活——从不被存储;Agent 只能看到经过对话的东西。

## Agent 层

Agent 层在 `src/app/api/agent/`,聊天回合与任何后台循环共用:

| 文件 | 用途 |
|------|------|
| `agent.ts` | 创建 `WorkflowAgent`,配置模型、思考、工具集 |
| `tools.ts` | 工具定义(schema + context schema)——聊天 Agent 的工具集 |
| `tool-executors.ts` | 每个工具的独立 `"use step"` 执行器 |
| `register-model-classes.ts` | 注册模型 host,使它们能跨 workflow→step 边界重建 |

### 工具

聊天 Agent 拿到的是一套小而克制的工具——**分工,而不是硬撑**。主模型统筹全局,具体工作派给各司其职的专职 agent,每一次派发都是一次可见的工具调用。

指针优先的记忆读取,从最便宜到最贵:

| 工具 | 用途 |
|------|------|
| `readSliceSummary` | 只读 Slice 的 frontmatter——focus、summary、标签、开放事项。廉价的相关性检查 |
| `readTimelineWindow` | 按日期窗口读时间线目录——每个 Slice 一行指针,用来按时间定位 |
| `readSlice` | 真正的对话原文——最后手段。可选 `range`(指定轮次 / 最近 N 轮 / 日期 / 搜索 / 行区间) |
| `readPreviously` | 读取某个 Slice 的用户卡片快照,当前或历史版本 |
| `readAgentTimeline` | 读取 Agent 自己在某个 Slice 的过去推理 |

专职 agent 派发:

| 工具 | 用途 |
|------|------|
| `recall` | 回忆 agent——把真正的搜索交给 worker 模型的回忆引擎,只返回指针,不返回内容 |
| `webSearch` / `webFetch` | 搜索 agent——联网检索带来源的答案,再做针对性的页面读取 |
| `thinkDeep` | 思考 agent——主模型的一个只思考副本,以 low / medium / high 三档力度独立推理一个自包含的片段;实质性的回合先拆成片段再作答 |

> **回忆一次,然后停止。** 主 Agent 不自己浏览记忆——探索是回忆引擎的活。它调用一次 `recall`,用 `readSlice` 读需要的内容,然后继续。原始的浏览工具(`listSlices`、`readTimeline`、`listStrands`、`readStrand`)留给回忆引擎和循环工具集。`startLoop` 在 `tools.ts` 里已定义但被注释掉(后台循环在稳定化期间暂时禁用)。

整理也是专职工作:标签、Strand、用户卡片都由 worker 模型在日常维护中更新——主 Agent 从不在回答中途做这些。`thinkDeep` 片段复用本轮已解析的主模型,并共享组装好的系统 prompt 作为前缀,因此供应商的 prompt 缓存在一个回合内横跨主调用与子调用。

## 双层模型分工

模型层(`src/lib/models/`)解析出两层:

- **主模型** —— 用户在聊天工具栏选,持久化到 `memory/user/config.json`。负责推理、工具调用、生成回答。
- **worker 模型** —— 从主模型供应商派生的廉价档(或手动固定)。跑日常维护调用:回忆扫描、元数据维护、语义门、Strand 整理。这样每轮成本低,重活交给主模型。

`resolveWorkerModel()`(`src/lib/models/worker.ts`)的选择顺序:手动固定 → 同供应商轻量档 → 主模型。目录是 models.dev 驱动的(`src/lib/models/catalog.ts`),以配置的 API key 环境变量为门槛,并按各供应商实时 `/models` 端点反过滤。

## 前端架构

Next.js App Router 强制执行严格的服务器组件/客户端组件边界。`page.tsx` 是一个服务器组件,预加载用户配置、设置演示人格,然后渲染 `ChatPage`——一个持有 AI SDK `useChat` hook(配 `WorkflowChatTransport`)的轻量客户端外壳。

页面是一个垂直滚动器:

1. **Hero** —— 服务端渲染的 `"Previously on {名字}"`。
2. **吸附的横向时间线** —— `HorizontalTimeline`,一排日期圆点,吸附在 AppHeader 下方。
3. **聊天内容** —— 实时消息;选中过去的圆点时是历史 Slice 视图。
4. **吸附的输入栏** —— 带模型选择器、思考开关、图片附件和演示触发按钮。

消息渲染是一条统一流式管道(`src/lib/chat/build-stream.ts`):推理合并进 `ThinkingSteps`,工具调用按 `toolCallId` 合并进 `ToolRenderer` 卡片,`data-phase` 部分变成 `PhaseIndicator`,`data-evolution` 部分驱动每条气泡的 `EvolutionIndicator`。一切通过 `AnimatePresence` 内联渲染在助手气泡内。

## 安全模型

安全完全在 TypeScript 的工具边界强制执行。

### 路径白名单

`src/lib/whitelist/index.ts` 定义仅有的三个可写目录:

```
memory/   tasks/   sessions/
```

`normalizePath()` 解码 URI 组件、把反斜杠转正斜杠、解析 `./` 与 `../` 片段、去掉前导斜杠。`isPathAllowed()` 拒绝空路径和绝对路径(Unix 与 Windows 盘符),然后检查路径是否以三个允许前缀之一开头。

### `src/` 是 Agent 只读

`src/` 目录根本不在白名单里。没有 Agent 工具能写进去。Agent 可以通过 git 读 `src/`,但不能改——路径白名单拒绝写尝试。这保证代码库完整性独立于 Agent 的执行。

### 同源守卫

这是一个单用户、私有化部署的产品——刻意没有登录系统。取而代之的是,`guardRequest()`(`src/lib/security/origin-guard.ts`)把过路流量挡在昂贵的 POST 变更端点之外(`/api/chat`、`/api/loops`、`/api/episodic/flush`):

1. `Origin` 头的 host 与请求自身 host 一致 → 同源浏览器请求,放行。
2. 没有 `Origin` 但带 `Sec-Fetch-Site: same-origin` / `same-site` → 放行。
3. 其他一切(curl、脚本、定时任务、跨站提交)必须发送等于 `ACCESS_SECRET` 的 `x-access-key` 头——但只在该变量被设置时。不设置,私有部署的默认体验保持无摩擦;运营者通过设置变量来选择启用密钥检查。

GET 流式回放端点与预检请求保持开放。

### Flush 端点约束

`POST /api/episodic/flush` 是浏览器在 `beforeunload` 时通过 `sendBeacon` 发出的紧急保存,把进行中的轮次追加到当前 Slice。因为 `sliceId` 会被拼进文件路径,在计算任何东西之前它必须先通过严格的 `YYYY-MM-DD-HHMM` 格式校验——一个宽松的字符串就是一个路径穿越漏洞。纵深防御:解析出的写入目标还必须落在显式允许集合内——该 Slice 自己的 `timeline/core.md` / `timeline/agent.md`——位于通用写工具拒绝触碰的、由系统管理的情景记忆区域里。

### GitHub Token 范围

`GITHUB_TOKEN` 限定为单个仓库的 contents 读写。Agent 只操作一个仓库:由 `GITHUB_REPO_OWNER` / `GITHUB_REPO_NAME` 定义的那个。没有跨仓库访问。

所有路径验证都在服务端——客户端不可信。浏览器从不构造文件路径或做存储决策。

## 数据源模式

存储有三种模式,由 `STORAGE` 控制:

| 模式 | 何时用 | 行为 |
|------|--------|------|
| `local` | 本地开发 | 读写本地文件系统 |
| `github` | 生产环境 | 通过 GitHub API(Octokit)读写你的仓库 |
| `demo` | 预览 | 只读,内置人格 |

自动检测:有 `GITHUB_TOKEN` → `github`;`NODE_ENV=development` → `local`;否则 → `demo`。
