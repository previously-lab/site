# Strands

Strand 是一个关键词,贯穿每一个携带它的时间切片——它是构建在情景时间线之上的语义层。切片按时间说"发生了什么",而 strand 按主题说"这是关于什么的"。

## 问题:情景记忆没有主题索引

时间切片按时间顺序组织你的历史。你可以问"昨天下午发生了什么",然后找到对应的切片文件。但你无法轻易地问"所有我说过关于 Rust 的事情"——这个问题是*跨时间*的,而不是沿着时间的。

你需要两个坐标轴:

| 记忆类型 | 组织方式 | 单元 | 回答的问题 |
|---|---|---|---|
| **情景记忆** | 时间 | Slice | "什么时候发生了什么?" |
| **语义记忆** | 主题 | Strand | "关于 X 说过什么?" |

Strands 填补了语义轴。它们是按时间记录的切片在按主题维度的对应物。

## 工作原理

每个切片的 YAML frontmatter 中包含 `tags`——像 `"rust"`、`"async"`、`"deployment"` 这样的关键词。每当一个切片关闭时,这些标签会被编织进一个全局文件:

> `memory/episodic/strands.json`

该文件中的每个键是一个 **strand**(一个标签)。每个键的值是标记了该关键词的所有切片相对路径列表——"那个东西的完整历史"跨越时间。

```json
{
  "rust": [
    "2026/06/22/1400",
    "2026/07/01/0915",
    "2026/07/08/1630"
  ],
  "async": [
    "2026/06/22/1400"
  ],
  "deployment": [
    "2026/07/08/1630"
  ]
}
```

路径是相对的:没有 `slices/` 前缀,也没有 `.md` 扩展名。`sliceIdToRelPath` 将像 `2026-06-30-1430` 这样的切片 id 转换为 `2026/06/30/1430`,这样你就可以直接访问 `memory/episodic/slices/2026/06/30/1430.md`。

## 派生而来,而非手动编写

Strands 没有单独的编写步骤。它们**完全派生自**每个切片 YAML frontmatter 中的 `tags` 数组。标签由 worker 模型在其维护更新中每轮维护——它读取对话、分类主题并写入标签。这些标签自动成为 strand。

这个循环是:

1. **worker 运行元数据维护** → 将 `tags` 写入当前活跃切片的 frontmatter
2. **切片被持久化**(在默认约 15 分钟静默后关闭,或在对话中做快照)
3. **`updateStrands(slice)` 运行** → 读取 `strands.json`,将每个标签编织为键,追加切片的相对路径(去重后),写回

编织是**合并优先**的:标签在创建新键之前会先被规范化(去除首尾空白、ASCII 转小写、全角折叠为半角、合并内部空白),并与现有键匹配——所以 `Apex` 和 `apex` 会落在同一个 strand 上,而不是把一个主题拆成两个。只有真正新的标签才会创建新键。

标签编织成 strand。你永远不会直接编写 strand。

## Strands 何时写入

`updateStrands` 在两个地方运行:

- **切片关闭时**(`manager.ts` 中的 `closeSlice`):在切片 `.md` 文件写入并且月度 `_index.json` 更新后,`updateStrands` 将切片的标签发布到全局索引中。
- **活跃切片快照时**(`manager.ts` 中的 `ensureIndexEntries`):当对话进行中保存快照时,`updateStrands` 也会运行——但仅当该切片至少有一个标签时。这意味着进行中的切片在关闭前就会出现在 strand 索引中。

结果是:即使是活跃切片,`strands.json` 也始终保持最新,因此回忆扫描永远不会因为切片尚未关闭而错过某个标签。

## 保持索引干净

一个只会追加的索引会腐坏:错别字把一个概念拆到两个键上,而一年前只用过一次的标签会永远留存。每次切片关闭时,都会运行一个整合过程(`consolidateStrands`),分为两个阶段:

1. **确定性修剪(总是执行)。** 从未成为线索的 strand 会被修剪——具体来说,是切片数少于 2 且所有切片都超过 14 天的 strand。只要 strand 有足够的切片*或*至少有一个最近的切片,它就能存活,所以真正的新主题绝不会在出现当天被剪掉。
2. **LLM 合并过程(仅当索引有 25+ 个 strand 时)。** 规范化能捕获 `Apex`/`apex` 这类机械性重复,但 worker 模型本身也会制造语义重复——名字中的错别字、同一概念的两个名字。worker 模型审查索引并提出一个 from→to 合并映射(每次最多 30 条合并,精确率优先于召回率:有疑问时不合并)。然后工程层合并路径列表并移除冗余的键。

整个过程是防御性的:任何失败都会原样返回索引,因此切片关闭永远不会因为整合而中断。

## Strands 如何被读取

这个索引不是只写的——它通过三条路径在每一轮喂养给 agent:

- **记忆主题菜单。** 在每轮的维护期间,系统提示的可变尾部会加入一个 `## Memory topics` 块:最多 20 个 strand,按最近活跃切片排序,每个都标注了最后一次出现的时间。当用户提到这些主题之一时,主 agent 被指示运行 `recall`。
- **回忆管道。** `recall` 工具把查询交给一个 Flash 子 agent,它只通过指针搜索记忆。这个子 agent 预先拿到 strand 列表,被指示检查哪些 strand 与查询匹配,并拥有自己的 `readStrand` 工具来把匹配的 strand 追踪到携带它的每一个切片路径。Strands 是回忆的主题轴;`readTimelineWindow` 是时间轴。
- **时间线投影。** 每次 `weaveTimeline` 都会读取一次 `strands.json`,并解析出每个时间线条目的 `strands` 字段——切片标签中已被编织为 strand 的子集。结构化的时间线索引因此记录了哪些 strand 穿过哪些切片,随时可供消费者使用,比如把 strand 渲染为平行时间线的 UI。

主 agent 本身不会直接遍历原始索引——`readStrand` 和 `listStrands` 属于回忆引擎。主 agent 看到的是菜单加上 `recall` 返回的结果。

## 类型定义

`StrandIndex` 类型(定义在 `src/lib/episodic/types.ts` 中)是一个普通的字符串键映射:

```typescript
interface StrandIndex {
  [strand: string]: string[];
}
```

如果 `strands.json` 还不存在——即没有任何切片有过标签——`readStrands()` 返回一个空对象 `{}`。写入总是通过 `JSON.stringify(index, null, 2)` 生成美化打印的 JSON。

## 双存储

读写路径通过 `fsReadFile`/`fsWriteFile` 包装器进行,它们在开发环境下透明地操作本地文件系统,在生产环境下则操作 GitHub API。strand 索引本身(`strands.json`)是一个运行时数据工件——它与切片位于同一个 memory 仓库中,而不是在应用源码树中。此代码仓库的工作树中不包含任何已提交的 `strands.json`。

## Strand 还不是什么(尚未实现)

<Callout variant="info">
Strand 仍然是一个轻量、无损的索引:从关键词到切片路径的映射,仅此而已。一个更丰富的**一等公民 strand**——拥有自己的滚动摘要、自己的元数据,并以平行时间线的形式可视化渲染——是一个明确的未来里程碑。v0.8 的时间线 schema 已经携带了每切片的 strand 归属,因此这个视图可以在不改动数据的情况下构建。
</Callout>
