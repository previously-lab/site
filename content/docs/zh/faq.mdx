# 常见问题

关于 Previously 如何工作、运行成本以及边界在哪里的常见问题。

## 有数据库吗?

没有。所有状态都是带有 YAML frontmatter 的纯 Markdown 文件,存储在 GitHub 仓库中。没有数据库、没有向量存储、没有 ORM,也没有专有格式。Slice、Strand、用户卡——一切都是文件。

索引只是几个 JSON 文件。全局目录位于 `memory/episodic/timeline/index.json`,列出所有 slice(并附带一个 Markdown 投影 `memory/episodic/timeline.md`);按月度的 slice 索引(`_index.json`)位于月份目录中;`memory/episodic/strands.json` 将每个 Strand 关键字映射到其对应的 slice 路径。每个 slice 是一个目录(`slices/YYYY/MM/DD/HHMM/`),其中的 `timeline/` 保存共享记录(`core.md`)和 agent 自己的认知记录(`agent.md`)。这就是全部"管道"了。没有 Postgres、没有 SQLite、没有 Pinecone。

<Callout variant="info">
**关键要点:你的记忆就是一个 git 仓库里 Markdown 文件的目录树。仅此而已。**
</Callout>

## 其他工具能读取我的记忆吗?

可以。记忆是带有 YAML frontmatter 的纯 Markdown——没有 SDK、没有 API 网关、没有供应商锁定。Previously 写入记忆。Claude Code 读取记忆。Codex 扩充记忆。任何能解析 Markdown 并读取 GitHub 仓库的工具都能读取你的记忆。

这种可移植性是核心设计目标。你永远不需要导出或迁移数据;只需让不同的工具指向同一个仓库即可。

## 在长对话中它会遗忘吗?

不会——不像不断增长的提示窗口那样会遗忘。Previously 没有无限累积的聊天线程。每一轮对话都会从头组装上下文,并且保持边界可控。

每个对话轮次都会构建一个全新的系统提示(`src/app/api/chat/turn-workflow.ts` 中的 `assembleSystemPrompt`)。稳定的块排在最前——身份章程和用户卡——这样提供商的提示缓存可以跨轮次复用这个长前缀。可变的尾部紧随其后:每轮简报(时间戳、意图、连续性)、近期时间线条目块,以及 Strand 菜单。随请求发送的可见聊天历史由可配置的最近轮次上限约束(默认为 20)。

关键在于,时间线条目是指针而非内容本体。当某条记录看起来相关时,agent 会通过 `readSliceSummary` / `readSlice` 工具按需打开对应的 slice,而不是把数月的对话都塞进提示里。归档可以跨月增长,但加载到任何单次请求中的内容始终保持窗口大小。

不存在 agent 突然忘记长对话开头的情况,因为根本没有单一的长对话——上下文每轮都会重建。

## 切片是如何关闭的?

三个触发条件,在每个对话轮次的 housekeeping 步骤中检查(`src/app/api/chat/steps.ts`):

- **静默超时**——一段时间无活动后 slice 关闭(默认 15 分钟)。
- **轮次上限**——强制关闭超长会话的安全阀(默认 20 轮)。
- **上下文丢失**——如果客户端回来时没有任何 assistant 历史记录,而恢复出的 slice 已有 agent 轮次(页面刷新、更换设备),旧 slice 会被关闭并开启一个新 slice。

两个阈值都可以在设置中调整——它们存放在 `memory/user/config.json` 中:

```json
{
  "slicing": {
    "maxTurnsPerSlice": 20,
    "timeSilenceMinutes": 15
  }
}
```

当 slice 关闭时,其元数据被冻结,时间线目录和 Strand 索引随之更新,下一条消息会开启一个新的 slice。

## 它达到生产就绪了吗?

没有。Previously 是实验性的(v0.8)。README 带有"实验性"状态徽章,并明确说明"尚未准备好用于个人或生产用途"。

这是个人部署,而非 SaaS 产品。作者承诺长期维护,但项目处于活跃的早期开发阶段。预计会遇到粗糙的边缘、破坏性变更以及仍在路线图上的功能。

## 代码和记忆共享同一个仓库吗?

可以共享,也可以分开。部署后的应用读写由环境变量 `GITHUB_REPO_OWNER` 和 `GITHUB_REPO_NAME` 指定的 GitHub 仓库。这些环境变量也可以指向一个与代码仓库不同的专用私有记忆仓库。

项目自身的约定(在 `CLAUDE.md` 中描述)将代码和数据放在同一个仓库中——其中 `src/` 为 agent 只读,而数据目录(`memory/`、`tasks/`、`sessions/`)为 agent 读写。但配置给了你选择权。独立的记忆仓库也是可行的,并在[快速上手](/docs/getting-started)中有文档说明。

## 运行成本是多少?

两个成本中心:

- **LLM API 使用费**——Previously 使用你自己的 API 密钥运行。支持九家提供商(DeepSeek、Anthropic、OpenAI、Moonshot AI、Alibaba、Google、Mistral、xAI、Groq);你设置了哪些密钥,就决定了可用的模型。两层架构是出于成本考虑:廉价的 **worker 模型**处理 housekeeping、召回扫描和用户卡演化,而**主模型**(由你选择)只保留给对话本身。
- **托管费用**——Vercel(部署按钮指向 Vercel)。Vercel 的免费套餐可能覆盖轻度使用,但持续使用可能需要付费计划。GitHub 仓库存储基本上是免费的。

Previously 不收取任何订阅费、按席位收费或使用加价。你提供基础设施和密钥;该项目是介于两者之间的编排层。

## 我的数据隐私吗?

是的,这是设计使然。记忆存储在你拥有的 GitHub 仓库中(推荐使用私有仓库)。访问由 GitHub fine-grained personal access token 控制,该 token 限定为单个仓库的 contents 读写权限。没有保存你对话的平台数据库。没有第三方服务器存储你的 slice 或 Strand。

在 HTTP 层面,变更类接口(`POST /api/chat`、`/api/loops`、`/api/episodic/flush`)有同源保护;当设置了 `ACCESS_SECRET` 时,非浏览器调用方还需要携带访问密钥。LLM 提供商显然会看到你发送的提示——这是唯一的外部数据通路,也是使用任何托管模型所固有的。

你完全拥有数据的所有权。克隆它、备份它、迁移到其他供应商——它们只是 git 仓库中的文件。
