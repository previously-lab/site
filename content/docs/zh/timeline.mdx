# 时间线

时间线是 Previously 的中心,它以两种形态存在:一是你滚动的**界面**——对话旁一列按日期排列的 Slice 滚轮;二是 Agent 导航的**记忆索引**——一份从 Slice 文件重建的目录,让 Agent 拥有你过去的地图。两者都是同一真相来源的投影:Slice 本身。

## 不是聊天列表,也不是搜索栏

时间线是大多数 AI 聊天产品采用的两种主流 UI 模式的明确替代方案。它**不是**需要你手动管理、重命名、删除和搜索的对话线程列表。它**不是**一个输入关键词、期望正确记忆浮现的搜索栏。这两种模式都把负担推给人类——它们假设你会自己整理记忆。

Previously 摒弃了这一假设。取而代之的是一条单一时间线——你的故事如同一部自传,最旧的在顶部,最新的在底部,实时对话在「现在」一端。

<Callout variant="info">
**关键要点:你不需要管理对话。你只需滚动你的人生。**
</Callout>

## 界面:对话旁的滚轮

聊天页是一个分栏视图。左侧是**时间线滚轮**(`TimelineWheel`),右侧是对话——实时或历史。屏幕底部是固定的输入栏。

滚轮是一条垂直的、虚拟化渲染的列表,包含**你所有的 Slice**,一次性从时间线目录加载——最旧在顶,最新在底,末端是一行「现在」,选中即回到实时对话。关键行为:

- **行 = Slice** — 每行显示 Slice 的日期、时间与 focus 行。当前加载的 Slice 所在行是品牌色;悬停会提亮其他行。
- **滚动数字** — 时间戳随滚动以里程表方式上下翻动,穿越过去如同拨动时钟。
- **滚动或拖拽** — 向下滚动露出更早的 Slice,向上回到现在。想看完整目录时,滚轮就地展开(加宽并覆盖内容,背后有模糊遮罩),选中一个 Slice 后收起。
- **两档形态** — 桌面端滚轮显示完整行;手机上收窄为锁屏时钟式样的窄条(小号日期叠在大号小时与分钟之上)。

选中过去的 Slice 会播放一段**时间旅行过渡**:一个滚动数字时钟从你当前位置转到目标 Slice 的时刻,上方是加宽字距的 "PREVIOUSLY ON" 眉题,随后历史视图淡入。

## 抵达简报

当实时聊天为空——初次抵达,或上一个 Slice 关闭后回来——右侧面板显示**抵达简报**,而不是空白画布:电影标题卡式的 "PREVIOUSLY ON" 叠在你的名字之上,然后是从真实记忆生成的热启动摘要:

- **上次话题** — 最近一个 Slice 的 focus 行。
- **未决事项** — 最多四条延续至今的未结线索。
- **建议 chips** — 一键发送的提示词,来自上次话题、未决事项和最近的 Slice。每个 chip 都会真实发送一条消息。
- **查看完整 previously** — 打开当前 Slice 的 `previously.md`(Agent 的紧凑用户卡快照)对话框。

每个区块只在有真实数据时渲染——不会出现"上次聊到"后面什么都没有的情况。演示模式下,你的名字即人格切换器。

## 历史 Slice 视图

选中过去的 Slice,右侧面板切换为历史视图,滚轮保持不动:

- **Previously On 栏** — Brain 图标 + 标签;点击打开包含该 Slice `previously.md` 快照的对话框,下方是该 Slice 的摘要行。
- **历史轮次** — 带时间戳的用户/Agent 往返;每个 Agent 轮次可通过「思考」popover 查看当时的想法(认知日志)。
- **未决事项 / 决策页脚** — 该 Slice 的未决事项(↗)与决策(✓),以带标签的胶囊显示。

## 索引:投影,而非第二个真相

自 v0.8 起,时间线同时是 Slice 档案之上一等的、持续维护的**索引**。设计原则是:

<Callout variant="info">
**Slice 是唯一真相来源;时间线是派生投影。** 目录中的每个条目都能从 Slice 文件重建,因此一个 Slice 永远不会因为"时间线弄丢了它"而失联。
</Callout>

索引以同一结构的两种渲染存在,都位于 `memory/episodic/` 下:

- **`timeline/index.json`** — 规范的结构化目录,供 UI(滚轮由此渲染)和工具消费。
- **`timeline.md`** — Markdown 投影,按 era(月份)和日分组,最新在前。这是 recall agent 当作地图读取的文件。

每个目录条目是一条**带质感的指针**——id、日期、起止时间、轮数、状态、`focus`、`summary`、`tags`、情绪 `tone`、`open_loops`、`decisions`、所属的 `strands`,以及 `needs_marking` 标志。一行足以判断相关性,但永远不足以据此作答:

```
- **2026-08-11-1115** 回顾滴滴时期绩效背锅/晋升被吃,与当下对比 · 14轮 · mixed [状态回忆,创伤克服,人生思考]
```

## `weaveTimeline`:工程化对账

索引由 `weaveTimeline`(`src/lib/episodic/timeline/weave.ts`)维护——一个确定性的流程,在每回合 housekeeping 开始时运行,**零模型调用**:

1. **枚举** 真实存在的 Slice 目录——即真相。GitHub 后端下这是一次递归 Git Trees API 调用;本地则是一次文件系统遍历。
2. **加载** 当前投影(首次运行时从旧的月度 `_index.json` 迁移)。
3. **Diff** — 磁盘上存在但目录里缺失的 Slice,从其 frontmatter 补入;目录里有而磁盘上没有的条目(幻影)被丢弃。**Slice 永远胜出。**
4. **重建** — 对照 `strands.json` 解析 Strand 归属,按时间排序,写出两种视图。在回合内,这些写入并入该回合的同一个 git commit。

全量对账有节流(目录新鲜度在 5 分钟内则跳过),所以每回合的 weave 通常只是一次缓存读取;Slice 关闭路径会强制对账,让刚关闭的 Slice 立即可见。由于对账是结构性的,孤立 Slice——已创建但从未入索引、跨日才关闭——都会被自动拾起。

## `needs_marking`:干 Slice 队列

关闭时没有 `focus`/`summary` 的 Slice 是**干 Slice**——对 recall 而言是匿名的。weave 把它们标记为 `needs_marking` 而不是藏起来,并有两个机制让这个计数持续下降:

- **关闭时的确定性兜底** — 当分析器产出的关闭标记不完整时,Slice 会以确定性标记关闭(首轮话题 + tags),而不是留空字段。
- **回填** — 只在 Slice 关闭的边界(绝不在回合进行中),一个 worker 模型批次(`backfill-marks.ts`)为少量干 Slice 写入 focus/summary 并清除标志。契约上是尽力而为:回填失败绝不会拖垮一个回合。

## Agent 看到什么

每回合,housekeeping 从目录构建一份**时间线简报**,追加到系统 prompt 的可变尾部:

```
## Timeline (recent)
- **2026-08-11-1115**(08-11 周二 · 6 天前)回顾滴滴时期… · 14轮 · mixed [状态回忆,…]
- **2026-08-10-1839** …
- 往前共 152 片,可用 readTimelineWindow / readSliceSummary 回溯
```

大约十条最新的指针行,每行带用户本地日历标注(星期 + 相对天数,Agent 无需做日期心算),外加目录总数与干 Slice 计数。prompt 里写得很明确:*时间线的行是指针——某行看起来相关,先读 Slice 再作答。*

随后的读取沿成本阶梯进行——先用最小的足够单元:

| 工具 | 返回 | 层级 |
|------|------|------|
| `recall(query)` | recall 同事带原文引用的回答 | 1 — 主要的过去访问 |
| `readTimelineWindow(from?, to?)` | 日期窗口内的指针行(默认 20,上限 50) | 1 — 按时间定位 |
| `readSliceSummary(sliceId)` | 仅 frontmatter:focus、summary、tags、tone、loops、decisions | 1 — 相关性检查 |
| `readStrand(strand)` | 一个 Strand 的 Slice 路径 | 1 — 追踪话题 |
| `readSlice(sliceId, range)` | 指定轮次 / 最近 N 轮 / 某时间之后 / 关键词命中 / 行区间 | 2 — 需要原文 |
| `readPreviously(sliceId)` | 该 Slice 的用户卡快照 | 2 |
| `readSlice(sliceId)` 全量、`readAgentTimeline` | 整个 Slice / 认知日志 | 3 — 明确的最后手段 |

recall agent 用同一张地图:分页读取全局时间线(最新在前),更早的区间用 `readTimelineWindow`,并始终停留在摘要层——深读是主模型的职责。见[回忆](/docs/recall)。

## 三条时间线

有一处命名重叠值得说明:每个 Slice *目录*内还有一个 `timeline/` 子目录——那是落地页所说的**三条时间线**中的单 Slice 一对:

- **`core.md`** — 共享记录:你和 Agent 实际说过的话。
- **`agent.md`** — 它的思考:每个轮次背后的认知日志。
- **你的生活** — 只有你知道的第三条线;永远不会被写下的部分。

本页所讲的全局时间线是所有 Slice 共享记录之上的目录——让上百个 Slice 可作为一条线来导航的索引。

## Slice 存放在哪

每个 Slice 是 `memory/episodic/slices/YYYY/MM/DD/HHMM/`(UTC)下的一个目录,内含 `previously.md` 与 `timeline/core.md` + `timeline/agent.md`。你开口时 Slice 打开,默认约 15 分钟沉默后关闭(可配置)——由时间驱动,轮次上限作为兜底。详见 [Slices](/docs/slices)。

## 数据流(UI)

界面通过 server actions 填充:

1. **初始加载** — `getEpisodicState()` 返回最近的 Slice 为 `active`、一组 `recent` Slice 和 `hasMore` 标志;用于填充简报与发送窗口。
2. **滚轮** — `getTimelineCatalog()` 从 `index.json` 返回完整目录(最旧→最新,客户端虚拟化渲染);没有逐页拉取。
3. **Slice 内容** — `getSliceContent(slice_id)` 在选中时懒加载 Slice 的轮次、摘要、previously 快照、未决事项与决策。
