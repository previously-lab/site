# 召回

<Callout variant="info">
在 v0.5 中，agent 自行决定何时搜索你的过去。它自主调用 `recall` 工具——一个快速的 Flash 子 agent 扫描全局时间线和 strand 索引，返回指向相关 slice 的指针，然后主模型读取它需要的内容。不再在每次回复前强制注入上下文。
</Callout>

Recall 是 agent 查找相关过往对话的方式——不是由系统在每轮对话前预加载上下文，而是由 agent 自主决定何时需要查找某件事。

这一转变——从 Push 到 Pull——是 v0.5 最深层的架构变化。

## Push → Pull：为什么重要

在 v0.4 中，每轮对话的流程如下：

```
Flash（必须运行）→ 组装上下文 → Pro（被动接收）
```

在 agent 能够回应任何内容之前——哪怕是一句简单的"你好"——系统都会执行一次强制性的 Flash 调用。它分类意图、扫描最近的 slice 摘要、组装上下文块，并将所有内容喂给主模型。agent 对此没有选择权。上下文是被推送（Push）给它的。

在 v0.5 中：

```
你发送消息 → Pro 收到消息和你的 previously.md → Pro 决定：
  "我需要更多上下文吗？"
    ├─ 不需要 → 立即回复
    └─ 需要 → 调用 recall → Flash 搜索 → Pro 读取结果 → 回复
```

系统提示词中包含 `previously.md`——agent 对你的理解。这是唯一预加载的上下文。其余所有内容由 agent 按需拉取（Pull），在它判断对话确实需要时才获取。

**这为什么重要：**

- **延迟**——不涉及过去的对话（问候、简单问题、快速追问）完全跳过 Flash 调用。agent 回复更快。
- **Token 成本**——不需要的上下文不消耗提示词预算。当你询问天气时，agent 不需要为读取你的装修项目而付费。
- **自主性**——agent 决定何时搜索、搜索什么、读到多深。它不是预组装上下文的被动接收者。它是自身记忆检索的主动参与者。

这是一个喂养模型的系统与一个使用工具的模型之间的区别。

## Recall 如何工作

当 agent 决定需要查找某件事时，它调用 `recall` 工具。这会启动一个 **Flash 子 agent**——一个快速、轻量的 DeepSeek 模型，执行多步探索：

### 第 1 步：读取全局时间线

Flash agent 首先读取 `memory/episodic/timeline.md`——一个包含你历史中每个已关闭 slice 摘要的单一扁平文件。一次读取，一览全貌。无需扫描目录，无需多个索引文件。agent 立即知道有哪些可用内容。

### 第 2 步：追踪相关 Strand

如果问题跨越时间按主题查询（"我讨论过的所有关于 Rust 的内容"），agent 读取 `memory/episodic/strands.json` 中的相关条目——全局关键词到 slice 的索引。每个 strand 将一个主题映射到所有携带它的 slice。agent 跨越时间追踪主题，找到纯粹基于新近度的搜索会错过的联系。

### 第 3 步：读取有希望的 Slice

基于时间线概览和 strand 追踪，agent 挑选最有希望的 slice，并使用 `readSlice` 完整读取它们。它在寻找匹配你问题的具体对话内容——不仅仅是摘要，不仅仅是元数据，而是实际的交流内容。

### 第 4 步：返回指针，而非摘要

Flash agent 生成一份结构化报告——不是它发现的摘要，而是一系列**指针**：slice ID、轮次编号和相关性评分。Flash 快速、廉价且近似。它不被信任来准确总结内容。它的工作是回答一个问题："主模型应该去哪里找？"

然后主模型通过 `readSlice` 直接读取那些 slice。实际内容未经过摘要、未经过滤地传递给主模型，完全按照记录时的原样。Flash 提供地图；主模型行走实地。

## 工具集

agent 拥有一套用于导航你过去的记忆概念工具。这些工具取代了 v0.4 中的旧文件系统概念工具（`readFile`、`writeFile` 等）：

| 工具 | 做什么 | agent 看到什么 |
|------|-------------|---------------|
| `recall` | 启动跨时间线的 Flash 搜索 | "正在搜索关于……的对话" |
| `readSlice` | 完整读取一个时间 slice | "正在读取 7 月 25 日的对话……" |
| `readTimeline` | 读取全局时间线索引 | "正在浏览时间线……" |
| `readStrand` | 追踪一个主题关键词跨 slice | "正在追踪 'rust' strand……" |
| `listStrands` | 列出所有已知主题关键词 | "正在浏览所有主题……" |
| `readAgentTimeline` | 读取 agent 自身的认知记录 | "正在回顾过去的思考……" |
| `readPreviously` | 读取历史自我模型快照 | "正在读取过去的印象……" |

这些不是重命名的 `readFile`。它们是语义上不同的工具。`readSlice` 构造 slice 目录的路径，读取 `core.md` 和 `agent.md`，并以结构化格式返回。`readStrand` 读取 strand 索引，找到正确的条目，并追踪路径到实际 slice。agent 导航的是**记忆概念**，而非文件系统。它从不看到或构造文件路径。

## 用户看到什么

当 agent 调用 `recall` 时，你会看到它发生。Phase Indicator 显示"正在扫描记忆……"阶段并带有计时器。当 recall 结果到达时，一张卡片出现，显示找到了多少对话以及它们为什么相关。当 agent 读取特定 slice 时，你看到"正在读取 7 月 25 日的对话……"——带有实际日期，而非通用标签。

工具名称是人性化的，因为工具卡片使用工具输出的真实数据来渲染。`readSlice("2026-07-25-0915")` 显示为"正在读取 7 月 25 日上午 9:15 的对话。"agent 正在搜索你的记忆，你可以看着它工作。

## 元数据维护

在 v0.4 中，强制性的 Flash 调用将元数据维护——更新活跃 slice 的 focus、summary、tags 和其他前置元数据——作为统一 Flash 传递的副作用来处理。

在 v0.5 中，元数据维护与 recall **解耦**。系统通过正常的 slice 生命周期维护 slice 元数据：slicer 定期更新活跃 slice 的前置元数据，关闭流程将其最终确定。recall 系统纯粹关乎检索——它搜索、返回指针、读取。它在搜索期间不维护元数据。

这种分离使 recall 保持快速和专注。元数据维护通过 slice 生命周期进行，而非作为记忆搜索的副作用。

## 为什么 Flash 返回指针而非答案

这里有一个深思熟虑的设计选择：Flash 快速、廉价且近似。它读取摘要和索引——而非对话的完整内容。如果让 Flash 总结它发现的内容，它将基于摘要的摘要来工作。错误会叠加。

相反，Flash 返回**指针**。它说"这三个 slice 可能相关，原因是。"主模型——能力更强、成本更高——读取实际内容。Flash 提供地图。主模型行走实地。

这种分工——快速近似搜索后跟彻底深入阅读——映射了人类的记忆过程。你不会一次记起所有事情。首先你会有一个粗略的感觉，知道某事*何时*发生、*关于什么*。然后你聚焦于特定记忆并回忆细节。这一双层设计不是优化技巧。它是一种对 recall 实际运作方式的建模。
